# External listing import foundation

This repository contains a server-side import core and a bounded adapter for a licensed partner JSON feed. The adapter is not connected to a provider and no schedule is registered. There is currently no approved source configured, so no external network request or real listing import can run.

## Storage and isolation

- External records belong in `externalAds`, separate from user-owned records in `ads`.
- A record has no `userId`, owner identity, payment identifiers, or promotion fields.
- Firestore clients may read only active imported records; client writes are denied. Import run summaries are admin-readable, and lock records remain server-only.
- The source and source listing IDs are stable; the document ID is derived from both, so retries update the same record. Canonical HTTPS URLs are also hashed per source, so URL variants and changed source IDs do not create duplicate listings.
- Category mappings are explicit. Unknown source categories are marked `needs_review`.
- Price is represented as amount plus currency only for a valid paid offer. Free, exchange, and unknown offers never become zero-priced listings.
- A source cannot run until permission has been affirmatively recorded and reviewed. Title and original-link rights are mandatory. Description, price, category, location, publication date, and images are only retained when the reviewed rights record names those fields. Image hosts are allowlisted by source configuration.

## Import execution contract

The partner adapter requires a fixed HTTPS endpoint on an exact allowlist, uses a server-only optional bearer token, and expects a JSON envelope `{ "items": [], "hasMore": false, "nextCursor": "..." }`. It adds a bounded `limit` and opaque `cursor` to the configured endpoint; it rejects arbitrary next URLs and redirects. Each item uses the canonical importer field names (`sourceListingId`, `originalUrl`, `title`, optional description/category/price/location/images/publication date, and optional canonical status `active` or `stale`). Provider-specific field and category mapping must be reviewed before activation. The adapter caps one invocation at 20 source rows. The underlying runner has bounded timeouts, retries and source locking. A complete inventory may mark records missing from a successful full snapshot as stale; partial runs, failed feeds, and delta feeds never do so. Stale updates are limited to one atomic batch of at most 450 documents. The runner also uses deterministic ID/URL de-duplication and secret-free run summaries.

The `EXTERNAL_LISTINGS_ENABLED` flag is opt-in and must be exactly `true` for the adapter runner to execute. The public callable `getExternalListingsConfig` exposes only this boolean to the catalog UI. With the flag unset or false, the adapter performs no network fetch or listing write, and the UI does not query or display already stored `externalAds`; ordinary user ads remain unaffected. Records are retained, so switching the flag back on can show still-active records. The browser checks the setting on page load; reload an already-open page after changing the server setting. The runner has no registered scheduled caller while there is no approved source. This avoids deploying a recurring no-op job and its associated cost. Once the feed owner supplies an authorized endpoint, schema and polling limits, add the scheduled caller at an interval accepted by that provider; do not guess the interval.

Activation configuration uses `EXTERNAL_LISTINGS_FEED_URL`, `EXTERNAL_LISTINGS_FEED_HOSTS`, `EXTERNAL_LISTINGS_SOURCE_ID`, `EXTERNAL_LISTINGS_SOURCE_NAME`, `EXTERNAL_LISTINGS_LISTING_HOSTS`, optional `EXTERNAL_LISTINGS_IMAGE_HOSTS`, `EXTERNAL_LISTINGS_RIGHTS_REFERENCE`, `EXTERNAL_LISTINGS_RIGHTS_REVIEWED_AT` (Unix milliseconds), `EXTERNAL_LISTINGS_PERMISSION_CONFIRMED=true`, `EXTERNAL_LISTINGS_RIGHTS_FIELDS`, and `EXTERNAL_LISTINGS_CATEGORY_MAPPINGS_JSON`. `EXTERNAL_LISTINGS_FEED_TOKEN` is optional and must be stored as a Functions secret when needed, never in a public Vite variable or feed URL. Set `EXTERNAL_LISTINGS_COMPLETE_SNAPSHOT=true` only when the provider confirms every page represents the complete licensed inventory; otherwise keep it false so missing rows are not treated as deleted.

The generic JSON fetch helper rejects redirects, restricts endpoints to reviewed HTTPS hosts, validates DNS destinations, and applies time and response-size limits. The next source-specific implementation must add provider-authenticated fetching and documented source rate limits, use fixed reviewed endpoints, and validate any provider cursor. It must not scrape pages or follow arbitrary `next` URLs.

## Catalog integration is intentionally pending

`HomePage` and `NearbyPage` still load all active user documents from `ads`, apply filters in the browser, and paginate after the full read. The Home page now displays external records in a separate, cursor-paginated block; each request shows at most 30 records and scans at most 500 documents before asking the visitor to continue. The two collections are not merged in the browser. Nearby remains user-listings-only because there is no tested geo-query path for external records. A future bounded user catalog should use a denormalized `catalogListings` projection maintained from user ads and authorized external records. A server endpoint should apply structured filters and stable indexed ordering, then return a bounded page with a cursor. Arbitrary substring search is not a native Firestore query; decide between a bounded token/prefix index and a dedicated search service before implementation. The projection adds a write and index-storage cost per changed listing but limits client reads to the requested page. Preserve currency in the projection and make price filters currency-aware; do not coerce a foreign currency into the existing PLN price field.

## Source status and schedule

No real source adapter is enabled. OLX's official API FAQ says it cannot access market data or other people's ads and only manages a user-authorized account. OTOMOTO's API access requires a business account and is for account/partner integrations; no general market-wide search feed was confirmed. Allegro's REST API terms prohibit presenting Allegro offers, including archived offers, on competing services. No source currently provides Ozen Board with a confirmed right to syndicate other sellers' listings, text and images. The next activation step is for the project owner to obtain from a provider or consenting sellers one written syndication grant plus its feed endpoint/schema and allowed polling interval. References: [OLX API FAQ](https://developer.olxgroup.com/faq), [OTOMOTO API access](https://www.otomoto.pl/news/jak-uzyskac-dostep-do-api), [OTOMOTO API FAQ](https://www.otomoto.pl/news/faq-api), [Allegro API terms](https://developer.allegro.pl/rules/).

### Additional candidates checked on 2026-10-24

- The official ePraca WebService covers active job offers nationwide, offers JSON files inside a ZIP response, and includes an original offer URL and status in its schema. It is not anonymously usable: the Ministry requires a signed application, business/system identity and caller IP, then issues an authorized partner name. Access is restricted to 17:00–07:00 and 20 requests per daily cycle. Terms allow external systems to receive offers after approval, but prohibit changing offer content, require hiding inactive offers, and require the ePraca logo on every imported offer. No request was submitted and no offers were fetched. References: [ePraca sharing terms](https://oferty.praca.gov.pl/portal/assets/for-integrators/warunki-udostepniania-ofert-pracy-z-systemu-ePraca.pdf), [ePraca integration manual](https://oferty.praca.gov.pl/portal/assets/for-integrators/instrukcja-pobierania-ofert-pracy-z-systemu-ePraca.pdf).
- The ePraca application asks for the caller IP. Cloud Run/Cloud Functions use a dynamic outbound IP pool by default; a fixed allowlisted address requires routing egress through VPC and Cloud NAT with a reserved IP, which has infrastructure and usage costs. This has not been configured. Reference: [Google Cloud static outbound IP documentation](https://docs.cloud.google.com/run/docs/configuring/static-outbound-ip).
- The public dane.gov.pl API lists machine-readable developer apartment price feeds; the inspected Senso dataset is CC0 1.0 and updates daily. Its item schema includes a unit identifier, type, price, area and availability status, but no per-unit original listing URL; the inspected dataset represents one developer, not a country-wide classified feed. It was not imported. References: [dataset record](https://dane.gov.pl/pl/dataset/5039,ceny-ofertowe-mieszkan-dewelopera-2025), [public API docs](https://api.dane.gov.pl/1.4/doc?urls.primaryName=DANE.GOV.PL+RDF+API).
- The e-Zamówienia BZP API is public and free, but it publishes public-procurement notices rather than consumer or business marketplace ads. It is not a suitable substitute for the requested catalog. Its current published rate limit is 30 requests per minute per IP. References: [integration/API scope](https://ezamowienia.gov.pl/pl/integracja/), [API terms](https://ezamowienia.gov.pl/pl/regulamin/).

The existing JSON-feed wrapper's 20-row limit is per invocation and counts consumed source rows, not newly created records; it is not a daily quota. A full ePraca snapshot cannot be safely connected to that wrapper as-is and guaranteed to yield 20 new cards per day: an inventory-aware selection/checkpoint and status reconciliation must be designed against the approved feed ordering and snapshot semantics first. No source adapter or schedule was added without that access and confirmation.

The repository already has separate admin-only `importOlxLeads`, `importAllegroLeads`, and `importOtomotoLeads` callables under `functions/src/leads/`. They scrape public result pages and store lead titles and links in `leads` (up to 50 per call); they are not connected to this importer or to the public ads catalog and were not invoked or changed here. Their source terms and permission basis still need a separate review before relying on them.

Firebase Functions v2 `onSchedule` is the natural future scheduler because the project already uses it. Do not add a scheduled job until a source is approved and configured: the current Firebase documentation lists Cloud Scheduler at $0.10 USD/job/month, with up to three jobs free per billing account, plus function, Firestore read/write/storage, and network charges. Exact usage cost depends on the feed size, run frequency, and Firebase region.

The generic import core has a 500-record default for internal/test use; the partner-feed wrapper hard-caps production invocations at 20 source rows. At that wrapper limit, the importer performs at most 20 listing upserts, up to 40 URL-deduplication queries, and at most 20 source records in the stale sweep, plus lock/run-log operations. Firestore bills document reads, writes, storage, index storage, and network separately. Scheduled Cloud Functions also use Cloud Scheduler; exact cost depends on polling interval, Firebase plan, region, query matches, retries, and feed response sizes.
